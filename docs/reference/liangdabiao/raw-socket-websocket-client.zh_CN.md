# ESP32-C3 上的裸 socket WebSocket 客户端

在 Octop Passport（把 LLM Agent 的回复流式打到设备屏幕上的语音终端，直连
自托管的 Octop 服务器）里攒下的经验。传输层是手写的 WebSocket 客户端，跑在
lwip 裸 socket 上——家族「esp_http_client 在 C3+lwip 不可用」的教训让组件
路线直接出局，而 WS 帧协议本身很薄。这个客户端扛过了一整天的真机调试；下面
是它踩过的坑，按被抓住的顺序排列。每一个的症状都长得像「服务端坏了」或
「按键没反应」，而不是 socket bug。

## 1. 投递帧时必须保留尾随字节（TCP 粘包）

收到一个 WS 帧并交付给应用时，接收缓冲里往往是
`[帧头][负载][下一帧的帧头字节]`——TCP 会把同一时段到达的帧合并在一个段里。
交付代码把负载搬到前面、`rx_len = payload_len`，**把尾随字节静默丢掉了**——
那是下一帧的帧头字节。流从此错位：后续每次解析都把负载字节当帧头，必然失败。

症状：**第一条**消息处理完之后链路立刻死，报帧头错误；之前的一切看起来正常。

修法：只剥帧头——`memmove(rx, rx + hl, rx_len - hl); rx_len -= hl;`——负载和
尾随字节都留在缓冲里，消费者在下一次 `poll()` 之前从 `rx[0]` 读取。

## 2. 超尺寸帧：丢弃判定要在完整性检查之前，否则每轮必断

Octop 服务端会推 `state_snapshot` 帧，其大小随会话历史无界增长，很快超过
4KB 接收缓冲。朴素写法的帧循环先查完整性（`rx_len < 帧头+负载 → 等更多`），
之后才考虑丢弃——比缓冲还大的帧**永远过不了**这一关，而 fill 函数拒绝往满
缓冲里读 → 两者之一报错断链。症状：**每一轮对话必死**，死在服务端开始回复
（推快照）的那一刻，而小帧一切正常。

修法：超尺寸判定放在完整性检查**之前**。超尺寸帧只消费帧头，记下
`discard_left = 负载长度`，循环里随到随丢（`discard_fin_pending` 记录分片
消息直到 `fin` 段）。连接保持；反正设备只关心 `token`/`done`/`error` 帧。

## 3. fill 函数必须始终阻塞等新字节

「把接收缓冲填满」的助手如果在缓冲非空时立刻返回，poll 循环就变成**纯空转**：
半帧留在缓冲里，consume 说「还要更多」，fill 说「已经有字节了」，永无止境——
CPU 烧满，饿死低优先级任务，直到任务看门狗报警。症状：输入完全失灵、无日志、
板子像死机。

修法：`fill_rx` 每次调用都做一次阻塞 `read()`（带调用方的超时）；「有进展」
的定义是「读到了新字节」，不是「缓冲里有数据」。

## 4. 排队的用户动作必须能熬过链路死亡

服务端会在空闲几十秒后关闭 dashboard 的 WebSocket 连接，所以设备大部分时间
处于重连窗口。如果排队的「发送本轮」标志被 `run_turn` 消费后、连接在回复帧
到来之前死掉，用户的按键就丢了——症状：状态栏明明显示*已连接*，按键却
「没反应」。

修法：一轮以**零帧收到**告终时，重新置位发送请求——重连循环会在新连接上
补发。另外用户取消的轮次要发协议 `cancel`；并且考虑自动换新线程（服务端
按线程逐轮串行处理，积压会让每个新回合干等几分钟、无任何帧）。

## 5. 保活：一次只改一个变量，并记录死亡原因

25 秒一次的客户端 ping **按节奏杀死了连接**（每次死亡间隔精确等于 25 秒），
而去掉它之后，仅靠服务端自己的 ping/pong 链路就无限存活。服务端为何如此并
不重要——重要的是调试方法：每个 `-1` 返回路径都把人类可读的原因写进
`ws->last_err`，原因直接显示在设备屏幕上。没有这个，「socket 错误」四个字
什么都说明不了。

## 让这一切可调试的方法

- **屏幕就是调试控制台。** USB-Serial-JTAG 的控制台 VFS 被截屏驱动改道后，
  实时日志基本不可靠；那就让同一张截屏带上诊断计数器（收到帧数、最近帧类型、
  token 计数、断链原因）——验证 UI 的截屏顺便完成排障。
- **只烧应用分区保留 NVS。** 迭代网络代码时只烧 `0x10000` 的应用分区，
  Wi-Fi 凭据和 Octop 账号原样保留——每次迭代不用重新配网。（完整合并镜像
  会清 NVS。）
- **在 PC 上复刻客户端。** 一个 ~100 行的 Python 脚本，握手和收帧语义与
  固件逐字相同，对真实服务器运行，复现了完全一致的失败并让帧变得可见——
  固件从此是照着「复现出来的失败」修，而不是照着直觉修。
