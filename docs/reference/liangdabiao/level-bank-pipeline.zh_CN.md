# 把关卡库整理成生成的 C 数组

在围棋闯关（兄弟仓库的围棋应用）()里攒下的经验。那个应用从网页版的
3564 关里挑出 154 关做成设备版。整条管线一页纸说得完，而里面每一条规矩，
都对应着一个曾经真实发生过的失败。

## 问题：内容是棋盘局面，设备要的是表

一关不是一条形状固定的记录。它带着最多 43 颗黑白子、一组带字母的标记点、
最多四条正解路径、一段长达 240 字的说明；32 道选择题还额外带题干和选项。

其中最容易漏掉的一条是：**一关是一棵树，不是一条记录。** 同一个局面下可以
有多条正解路径，而"对手怎么应"取决于玩家当前还匹配着哪一条。一行字符串表达
不了这件事，所以数据模型是一个结构体，上面挂一小串路径：

```c
typedef struct {
    uint8_t len;
    const uint8_t *moves;   /* 点下标序列，len 个 */
} wq_path_t;
```

其余部分刻意做得无聊：154 关就是一堆朴素的指针，约 6 KB，谁都能一眼看懂。

## 一个文件，一关一个区块，格式故意做得无聊

事实来源是 `tools/weiqi/levels.txt`。一关一个区块，键顺序固定，一行一个值：

```
== 001 fundamentals-rules-intro-3
chapter: fundamentals
kind: puzzle
title: <顶栏显示的关卡标题>
player: white
black: cg
white: bgchcf
mark: cross:dg
correct: dg
instruction: <题面，最长 240 字>
```

坐标是 9x9 窗口内的 goban 二字码（`aa` 左上、`ii` 右下）。棋子按颜色分两行
书写。正解路径以 `|` 分隔，每条路径是一串二字码，从玩家先手开始。

格式故意做得无聊，是为了让每一种错都变成响亮的失败。缺键、陌生键、重复键、
坐标落到窗口外、正解路径不是从玩家先手开始、某一行棋子数是奇数 —— 全部让生成器
直接中止，而不是悄悄发出去一关带着默认值的关卡。

**为什么是一个文件，不是一关一个文件。** 本仓库上一个应用用的是一章一个文件，
因为那时一章有几百行。这里一关只有九到十行短行，154 个文件就是 154 个 diff
噪声源，外加一个没人会去读的目录列表。一关一个区块放在一个文件里，改动照样
是一处一行的干净 diff，同时整库可以一屏滚完（1703 行）。

## 抽取器只跑一次，之后文件就是事实来源

`extract_levels.mjs` 里装着上一个应用换来的教训：**正解路径是数据，绝不能用
正则去刮。** 它用 esbuild **求值**网页版的 TypeScript 章节、直接读出来的对象，
而不是对源码文本做模式匹配。这么做还顺带解决了两套坐标方言的问题 —— 网页版
混用了 goban 二字码和 `b3` 这种跳过 *i* 列的人类坐标。

它是个**一次性的引导工具**：除非给 `--force`，否则拒绝覆盖已存在的 `levels.txt`，
文件头里也写明了这一点。否则就会出现两份事实来源 —— 而你改了关卡库，下次有人
重跑抽取器，改动就被无声地抹掉了。

## 裁剪，是一关可能悄悄变得无解的地方

网页版是 19x19，设备统一 9x9 —— 统一棋盘尺寸意味着只需要一套渲染、一套版式算术。
所以每一个候选关卡都要按"棋子 + 正解着法 + 标记点"的包围盒裁剪，在原始棋盘上
滑动一个 9x9 窗口（先试中心）。

**裁剪不是单纯的重新取景。** 切掉棋盘可能把一块棋从它的气上切断，也可能把
让"倒扑"成立的那几颗子切走。所以抽取器会在裁剪后的棋盘上**用完整规则重新校验
每一条正解路径** —— 气、提子、禁自杀、简单劫 —— 凡是变得无解的关卡直接丢掉，
再用窗口搜索把大部分救回来。

这么做得到的数字是：候选关卡里有 **94%（2696 / 2860）** 在裁剪并重新校验之后
仍然装得进 9x9 窗口。这是"统一用 9x9"这个决定能被留下来的唯一理由。

## 生成期的限制是算术，不是审美

和上一个应用同一条规矩，只是数字按这份内容重新推了一遍：

| 预算 | 值 | 怎么来的 |
| --- | --- | --- |
| 关卡标题 | 13 字 | 16px 一行：210px / 16px |
| 题面说明 | 240 字 | 可滚动的题面页，三屏 13 字行 |
| 题干 | 190 字 | 选择题题面页 |
| 选项文字 | 10 字 | 作答页要放得下三个选项 |

这些常量住在 `tools/weiqi/content.py` 里，生成器发现任何一关超限就**中止**。
界面从另一侧断言同一批数字（`main/wq_layout.h`），于是一关放不下会在生成期
失败，而不是在设备上渲染到屏幕外面去。

## `--check` 把「记得重新生成」变成一条规矩

`gen_content.py --check` 与 `gen_font.py --check` 会把生成物跟 `levels.txt`
和界面文案对一遍。`tools/validate.sh` 第一件事就是跑它们，所以**改了关卡却忘了
重新生成，会直接失败构建**，而不是发出去一个编译得过、跑起来还是旧内容的固件。

字库那一侧的检查还有后半段，是上一个应用教会我们补上的：它不只比码点**数量**，
而是解析生成的 `.c`、还原出「设备真能渲染的码点集合」，再跟当前清单求差集。
数量对得上而码点已经漂了的时候，屏上照样是空白框 —— 而一个只打印 `STALE`、
退出码仍是 0 的 `--check`，根本不算检查。

## 内容事实只有一处定义

`tools/weiqi/content.py` 被每一个需要知道内容的地方 import：C 表生成器、
字库清单生成器、宿主测试。 "一共多少关"和"一关可以有什么"只写在一个地方。

生成的 `main/wq_content.h` 把实测上限带回 C：

```c
#define WQ_LEVEL_COUNT 154
#define WQ_CHAPTER_COUNT 7
#define WQ_STONES_MAX 43
#define WQ_CORRECT_PATHS_MAX 4
#define WQ_CORRECT_MOVES_MAX 9
```

这些数字是**从真实关卡库里量出来的**，不是估的：选中的关卡里最大的初始局面
确实带着 43 颗子，最长的一条正解路径确实 9 手（平均 2.5 手）。界面拿它们开
缓冲，于是缓冲跟着内容走，而不是手工调一个值、然后被悄悄冲爆。

## 解析器拒绝什么

下面每一条都会中止，并且报出是哪一关：

- 区块缺键、有多余键，或同一个键出现两次
- `kind` 不在五种已知类型里
- 坐标落在 9x9 窗口之外
- `black:` 或 `white:` 一行里字母个数是奇数
- 正解路径的起手不是声明的那一方
- 标记的形状不在已知字形里
- 标题、题面、题干或选项文字超出各自预算
- 选择题的答案下标越界，或正确选项没有出现在题干里
- 需要移除目标的终局关却没有目标

在这里零容忍很便宜。上面每一条，否则都会变成一个"看起来能玩、实际上过不去"
的关卡。
