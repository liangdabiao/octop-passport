# 为 LVGL 裁剪中文字库子集

在围棋闯关（兄弟仓库的围棋应用）()里攒下的经验。设备带三档字库
（16 / 24 / 32 px），一共 **603 个码点** —— 480 个汉字加 123 个其它字符。
这是本仓库一族里最小的一份预算，而它之所以小，是因为清单是**推导**出来的，
不是**维护**出来的。

## 字符清单要推导出来，绝不手工维护

`tools/weiqi/gen_font.py` 从两个地方拼出清单：

1. `main/*.c|*.h` 里**字符串字面量**中的每个非 ASCII 字符（先剥掉注释，
   所以中文注释不占 Flash）；
2. `tools/weiqi/content.py` 说关卡库用到的字符集。

手工维护的清单，迟早会在某个人改完界面、忘记同步的那一刻开始漂。推导出来的
清单从构造上就不可能过期 —— 而生成的 `assets/fonts/charset.txt` 会把实际进去
的东西记下来：

```
# 码点总数：603（汉字 480，其它 123）
```

空格 `U+0020` 值得单独提一句：推导链上任何一步做 trim 都会把它弄丢，而丢了它，
界面上每一个空格都会变成什么都没有。

## 转换前逐个码点核对母字体

在调用转换器之前，脚本用 `fontTools` 载入母字体，把每个码点跟它的 cmap 核一遍。
缺字会变成**构建期报错并指名道姓**，而不是三天后在设备上发现的空白框。母字体是
Noto Sans CJK SC Regular（SIL Open Font License 1.1），它的 SHA-256 钉在脚本里。

## 三档字号、不压缩，以及为什么必须开「大字体」格式

三档按 16 / 24 / 32 px 生成，4 位每像素，`--no-compress`，`--format lvgl`。
不压缩是因为设备直接从映射进来的 Flash 读点阵，运行时没有理由再去解它。

`CONFIG_LV_FONT_FMT_TXT_LARGE=y` 在这里是**必须**的，原因是一个硬的 16 位上限：
LVGL 默认的文本格式把位图偏移存成 16 位字段，等于把一份字库的点阵卡在
65,536 字节。而光是 32px 那一档就有 **233,660 字节**。这个开关把该字段换成 32 位。

注意这个决定的形状：它取决于**当前**的字形数量，所以值得重新推一遍，而不是
沿用上一个应用的结论 —— 更小的子集完全可能把结论翻回去。

## 生成的 `.c` 文件多大，跟 Flash 占用没关系

三个生成文件加起来是 **2,857,006 字节的源码**，但在 Flash 里只占 **431,919 字节**：

| 档位 | `.c` 源码 | Flash 里的 `glyph_bitmap` |
| --- | --- | --- |
| 16 px | 464,759 B | 61,805 B |
| 24 px | 906,674 B | 136,454 B |
| 32 px | 1,485,573 B | 233,660 B |
| **合计** | **2,857,006 B** | **431,919 B** |

小了六倍半，因为每个字节都写成 `0xAB,` —— 每个字节的数据要六个字符的源码。
所以**永远不要**拿 `.c` 文件去推算分区大小或字库预算。

唯一可信的口径是**链接期 `.map` 里的 `glyph_bitmap` 段**：

```
grep -A2 "^ \.rodata\.glyph_bitmap" build/firmware/<sha>/FoloToy-AI-Passport.map
```

也不要试图去数源码里 `0xXX` 的个数：转换器对小于 16 的值只写**一位**十六进制
（`0x0,`、`0xf,`），用两位的模式去匹配会**少算将近一半**。

## 字库比代码旧，是最容易漏的一种错

这个失效模式有两个讨厌的地方：

- 字库跟界面对不上时，屏上是一排空白框，看起来像渲染 bug 而不像构建问题；
- 而最直觉的那种检查**抓不到它**：这里最初的 `--check` 只比对清单文件，
  过期时往 stderr 打印 `STALE`，**退出码仍然是 0**。一个在过期数据上照样通过的
  门禁，不算门禁。

所以 `gen_font.py --check` 现在做两件事，两件失败都非零退出：

1. 清单文件必须与源码推导出来的一致；
2. 生成的 `.c` 必须真的覆盖清单里的每一个码点。

第 2 条的做法是解析生成文件、把「设备能渲染的码点集合」还原出来。有两个细节值得
写下来，因为弄错任何一个都会得出**看起来像灾难**的结果（报告"每个字都缺失"）：

- 转换器输出**两条** cmap，**两条都要算**。一条是连续区间
  （`.unicode_list = NULL`，ASCII 就是 `range_start = 32, range_length = 95`）；
  另一条是稀疏表（`.unicode_list = unicode_list_N`），它的码点是**它自己**的
  `range_start` 加上表里的值。只算稀疏那条 ⇒ 把整个 ASCII 报成缺失；只算连续
  那条 ⇒ 丢掉全部汉字。可靠的判据是 `.unicode_list` 是不是 `NULL`，
  而不是看 `range_start` 的数值。
- 如果还原结果说**每个字都缺**，那一定是解析错了，不是字库错了。这个症状只有
  一个成因。
